01 / CASE STUDY

Contesto

Il repository nasce come progetto pratico per simulare le attività quotidiane di una filiale: clienti, conti, movimenti, personale, ATM, finanziamenti e investimenti. Non è software bancario di produzione e non gestisce denaro reale.

02 / CASE STUDY

La sfida

Separare la logica del dominio dall'interazione nel terminale e dalla persistenza. Le modifiche devono essere salvate nel database senza affidarsi a file CSV come sorgente principale dei dati.

03 / CASE STUDY

La soluzione

L'applicazione usa modelli Python, un controller applicativo, servizi CSV e un modulo Pandas. Le funzioni coprono anagrafiche, operazioni sui conti e analisi, mentre importazione ed esportazione CSV sono azioni esplicite.

04 / CASE STUDY

Architettura

La documentazione descrive una separazione ispirata a MVC: view/menu → controller → repository PostgreSQL. Le scritture usano transazioni e le operazioni sul saldo sfruttano blocchi di riga SQL. Pandas legge dal repository e può produrre grafici PNG.

05 / CASE STUDY

Risultati e sviluppi

Nel repository sono presenti unit test per dominio, CSV e interazioni SQL simulate, oltre a dati sintetici per le dimostrazioni. Non sono dichiarati test end-to-end automatizzati con PostgreSQL reale; l'uso resta didattico.

Fonti e limiti

La scheda riassume documenti pubblici del repository. I riquadri software sono illustrazioni e non screenshot; non vengono dichiarate metriche di produzione.
